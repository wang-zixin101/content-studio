### 2.4 发现的缺陷

**D8（低，维护风险）**：`author_analysis_samples` 用 `c.status='analyzed'` 作样本口径，而分析状态的「唯一控制状态」是 `analysis_state`。二者由 `set_status` 同步维护（`repository.py:132-136, 139-157`）。
**当前不产生错误结果** —— 因为 `analyzed` 只能由 `set_status` 写入（`set_analysis_state` 从未被以 `"analyzed"` 调用），两字段必然同步；且所有 `set_analysis_state` 调用点（`api/analysis.py:80/94/110`、`api/contents.py:169/245`、`jobs.py:95/376`、`batch.py:336`）都只涉及 `queued/unprocessed`，另有 4 处**紧接着**调用 `set_status` 补齐。
但这意味着「双状态字段」是一个长期维护风险：任何未来只写 `analysis_state` 的新代码都会让画像读不到数据。

**D9（中，功能未闭环）**：`content_performance` 的 5 个次级计数 —— `favorite_count`、`reply_count`、`retweet_count`、`quote_count`、`bookmark_count` —— **已正确入库但零消费**。它们不参与流量画像打分、不参与跨账号、不进入 WRITE，仅在内容详情页展示（`api/contents.py:301`）。流量画像的全部统计只使用 `view_count`。

**已正确实现的安全兜底**：
- `_strip_unfounded_edit_fields()`（`style_profile.py:200-234`）—— 没有真实修改数据时，**代码级**剔除 `deleted_expressions` / `added_expressions` / `replaced_expressions` / `what_he_deletes` / `disliked_expressions`，并清空 V2 的 `edit_preferences.frequent_*` 与 `anti_style.supported_by_user_edits`。不只靠提示词请求。

**缺陷 D5（中）—— 摘要丢弃 7 个键，且全量 JSON 被遮蔽**

`_build_summary()`（`style_profile.py:280-312`）只取：`voice_summary`、`common_openings`、`common_endings`、`common_expressions`、`common_tones`、`edit_patterns.frequent_deletions`、`edit_patterns.frequent_replacements`。

**未被摘要携带**：`confidence`、`uncertain_patterns`、`global_voice`、`signature_patterns`、`anti_style`、`x_modes`、`topic_bound_terms`。

而 `build_write_messages`（`prompts.py:357-362`）与 `build_candidate_write_messages`（`prompts.py:523-528`）都是：
```python
if style_summary:
    parts.append(f"## 全局风格档案\n{style_summary}")
elif style_profile:
    parts.append("## 全局风格档案\n" + json.dumps(style_profile, …))
```
→ **摘要非空时（只要 `voice_summary` 或任一个 common_* 列表有值就会非空），`profile_json` 全量永不发送。**上述 7 个键对 WRITE 输出不可见。

**缺陷 D7（低）—— 3–4 条时白算一版档案**

`MIN_CONTENT=3`（`style_profile.py:24`）允许 3 篇即建档案；而 `personalization.COLD_START_MAX=4`（`config.py`），COLD_START 阶段 `build_write_messages` 会**代码级硬清空**全部风格证据（`prompts.py:327-334`）。
→ mine 内容为 3–4 条时，档案会被计算并落库（消耗 1 次 STYLE AI 调用），但**任何 WRITE 都不会使用它**。5 条起进入 LEARNING 才真正生效。

**缺陷 D6（低）—— 无提示词版本指纹**

`analyses` 表**没有 `prompt_version` 列**（`db.py:71-104`）；`save_analysis()` 只写 `model` 与 `created_at`。`style_profile` 表**没有 `prompt_version` 列**；`save_style_profile()` 不记录。
对比：`rewrites.prompt_version` 与 `batch_jobs.prompt_version` **都有**（写入 `WRITE_PROMPT_VERSION`，`api/rewrites.py:80`）。
→ 无法回答「这一行分析结果是哪一版 ANALYSIS 提示词产出的」。在即将进行 V2→V3 切换的当下，这意味着**切换前后的数据无法在库里区分**。

## 四、重点 4：三条分析入口与 Schema 依赖面

### 4.1 三入口一致性

| 维度 | Realtime | Batch | External JSONL |
|---|---|---|---|
| 调用点 | `analyzer.analyze_content` | `batch._save_analysis` | `external_analysis` |
| 提示词 | `build_analysis_messages()` | **同一个** | `build_external_analysis_prompt()` —— **只包装不复制**，内嵌 `ANALYSIS_SYSTEM` + `ANALYSIS_SCHEMA_HINT` |
| 源码位置 | `analyzer.py:71-76` | `batch.py:55-76` | `prompts.py:708-724` |
| `temperature` | `0.2` | `0.2` | n/a（外部模型） |
| Token 上限 | **1500** | **2000** | n/a |
| `response_format` | `json_object` | `json_object` | n/a |
| 归一化 | `normalize_analysis()` | 同 | 同 |
| 落库 | `persist_analysis_result()` | 同 | 同 |
| **Schema 校验** | **无** | **无** | **`validate_analysis_v2()`** |

`persist_analysis_result`（`persistence.py:61-77`）是唯一共同写入口，副作用固定 4 项：`save_analysis` / `replace_content_tags` / `set_summary` / `set_status(analyzed)`。

**只有外部分析调用 `validate_analysis_v2`** —— 全项目仅 2 处：`external_analysis.py:710`（预览分类 `_classify_record`）与 `1026`（确认导入）。Realtime（`analyzer.py:77`）与 Batch（`batch.py:260`）直接 `normalize_analysis`。

**缺陷 D2（中）**：`normalize_analysis()` 对缺失字段返回 `None`、非法 `length_chars` 回退到 `len(raw_text)`（`analyzer.py:33-37`），**不抛错、不记录 schema_error**。因此内部两条路径产出的「残缺分析结果」会以 `analyzed` 状态落库，并静默进入写作画像与流量画像的样本池。

**缺陷 D3（中）**：`1500`（realtime）vs `2000`（batch）不一致 —— 同一套提示词在两条路径上得到不同的输出预算。
叠加本轮付费对照实验的实测结论：`mimo-v2.6-pro` 是**推理模型**，`max_completion_tokens` **包含 `reasoning_tokens`**（已在 `completion_tokens_details.reasoning_tokens` 中实测确认）。在 1500 预算下，96 次真实请求中出现 **约 48%（V2 47.9% / V3 60.4%）截断**。即：`analyzer.py:75` 的 1500 在真实语料上是**系统性不足**的。

### 4.2 替换 Schema 的影响面

**会直接受影响的读取点（按依赖强度排序）**：

| 依赖点 | 路径数/规模 | 源码位置 | 失效方式 |
|---|---|---|---|
| `validate_analysis_v2` 契约 | 59 路径 | `analysis_spec.py:68+` | 明确报错（唯一会报错的） |
| 外部分析 `schema_hash` 校验 | — | `EXTERNAL_ANALYSIS_FORMAT_VERSION=1` | 明确报错 |
| 写作画像 | **39 路径** | `repository.py:1171-1273` | **静默取空** |
| 流量画像 | **35 路径** | `performance_profile.py:466-480` | **静默取空** |
| 跨作者洞察 | **9 维度** | `cross_account.py:70-85` | **静默消失**（维度无值 → 不上榜） |
| 三候选策略上下文 | 4 张优先级表 | `rewrite_strategy.py:63-118` | **静默降级**（`_metric_map` 空 → 跳过） |
| 素材检索 | 3 字段 + tags/keywords | `retriever.py:99` | 静默降级 |
| `normalize_analysis` 扁平映射 | 13 字段 | `analyzer.py:31-53` | 静默 NULL |
| `ANALYSIS_SCHEMA_HINT` | 2106 字符 | `prompts.py` | 提示词与实际契约脱节 |

**关键结构性风险**：
`analyses` 表只有 13 个扁平列。**其余字段（含 `content_invariants` / `rhetorical` / `stance_engagement` / `microstyle` / `style_boundary`）的唯一落点是 `analyses.raw_json`**（`repository.py:1680-1711`）。
→ 若 V3 重命名或调整这些嵌套键，`raw_json` 写入**仍然成功**（原样存 dict），但所有读 `raw_json[path]` 的下游会**静默取空，不报任何错**。这是本次核查发现的最大结构性风险。

**不受影响的层**：`contents` 表与整个导入层、`content_performance`、`authors`、`account_daily_metrics` / `creator_goal` / `qualified_impression_snapshots`、`import_batches`、`rewrites`、`tags`。

**受影响的 UI 口径**：`api/contents.py:292` 的 `_to_detail` 使用 `repo.get_analysis()` 的 13 字段 → 内容详情页展示的字段集固定为 13 个，V3 新增字段不会自动出现在 UI。

## 七、一句话结论

现有工作台的**数据层与确定性统计层实现质量很高**（15 项功能经验证正确，0 AI 边界清晰、0/NULL 与作者规范化等细节都处理到位）；**问题集中在「数据到提示词的传递环节」** —— 9 项缺陷中有 5 项（D1/D4/D5/D3 及 D9）都属于「数据已存在或已计算，但没有正确送达消费方」，其中 **D1 是生产路径上的死分支，且被测试的构造方式掩盖**。

对即将进行的 ANALYSIS Schema 升级，最需要提前确认的一点是：**新增/改名的嵌套字段唯一落点是 `analyses.raw_json`，下游 39 + 35 + 9 + 4 组读取点会在键不匹配时静默取空、不报任何错**。
